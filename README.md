# 🤖 Smart Recreational Robot (หุ่นยนต์สันทนาการอัจฉริยะ)

**Firmware 2.3.1** — Interactive ทักทายครั้งเดียวแล้วหาทางต่อ เดินต่อเนื่อง ตั้งค่าอุปกรณ์ผ่านเว็บได้ 51 ค่า และใช้ pin เดิมทั้งหมด

สถาปัตยกรรมซอฟต์แวร์แบบ **Computer Science Modular & Non-Blocking State Machine** สำหรับ ESP32 ออกแบบเพื่อการใช้งานจริงในกิจกรรมสันทนาการ ค่าย กิจกรรมกลุ่ม และการศึกษา

| **Head Servo** | หมุนคอ/หันซ้าย-ขวา | `PIN 18` |

## 🎶 3. วิธีเพิ่มเพลงใหม่ (Add New Song)
ไม่ต้องแก้ HTML หรือเขียน `if-else` เพิ่มในโค้ดหลักเลย! เพียงทำ 2 ขั้นตอนใน [SongSystem.h](file:///c:/Users/KPG_G/OneDrive/Documents/Arduino/sketch_oct2a/SongSystem.h):

### 1) กำหนดตัวโน้ตเพลงด้วยสัญกรณ์ดนตรีสากล (Beats & Dynamics)
```cpp
const Note SONG_MY_SONG[] PROGMEM = {
  {NOTE_C5, N_QUARTER, DYN_MF}, // ตัวดำ ปานกลาง
  {NOTE_E5, N_QUARTER, DYN_MP}, // ตัวดำ นุ่มนวล
  {NOTE_G5, N_HALF,    DYN_F}   // ตัวขาว ก้องกังวาน (Forte)
};
```
*(หากใส่แค่ 2 ค่า `{NOTE_C5, N_QUARTER}` ระบบจะคำนวณไดนามิกอัตโนมัติให้ทันที)*

### 2) ลงทะเบียนใน `SONG_REGISTRY` พร้อมระบุ BPM
```cpp
const SongItem SONG_REGISTRY[] = {
  // ... เพลงเดิม ...
  {"mysong", "ชื่อเพลงภาษาไทย", "recreation", "🎵", 125, 0.82f, SONG_MY_SONG, sizeof(SONG_MY_SONG) / sizeof(Note)}
};
```
👉 **เมื่ออัพโหลดโค้ด ปุ่มเพลงจะปรากฏบน Web Dashboard ทันทีโดยอัตโนมัติ! ปรับความเร็วเพลงได้ง่ายๆ แค่แก้ตัวเลข BPM**

### 🎼 4 สไตล์เสียงเครื่องดนตรี (Instrument Timbres & Envelopes):
สามารถเลือกเปลี่ยนสไตล์เสียงบนหน้าเว็บได้ทันที 4 แบบ:
1. 🔔 **Music Box (กล่องดนตรีใสกังวาน):** คลื่นเสียงสั่นสะเทือนแบบกระดิ่งแก้ว ค่อยๆ คลายตัวนุ่มนวล ไพเราะที่สุด
2. 🎻 **Vibrato (เสียงร้องมีลูกคอ):** โน้ตที่ลากยาวจะมีลูกคอพริ้วไหวแบบเสียงร้องมนุษย์ (LFO 5.5 Hz)
3. 🎹 **Acoustic (เปียโน/คาลิมบา):** หัวโน้ตเคาะชัดเจน แล้วมีหางเสียง sustain อบอุ่น
4. 👾 **Chiptune (เกมบอย 8-บิต):** เสียงแนวเกมเรโทรคลาสสิก คมชัดและหนักแน่นด้วยไดนามิกของแต่ละจังหวะ

## 6. Dashboard และ Hardware Config (v2.0.0)

หลังอัปโหลด firmware ให้เชื่อม Wi-Fi เดิมหรือ AP `Robot-Recreation` แล้วเปิด IP ที่ OLED แสดง เว็บใช้ฟอนต์ในเครื่องและไม่ต้องใช้อินเทอร์เน็ต การตั้งค่า Wi-Fi, GPIO และ I2C address ยังอยู่ใน `Config.h` เดิม ไม่มี API ให้เปลี่ยน pin

เว็บมี 3 แท็บ: **ควบคุมหุ่นยนต์**, **ตั้งค่า Hardware**, **สถานะระบบ** รองรับจอมือถือ แท็บเล็ต และเดสก์ท็อป อนุญาตการซูมและใช้คีย์บอร์ดได้ รายการเพลง สีหน้า และท่าทางยังโหลดจาก registry เดิม

| หมวด | ค่าที่ปรับได้ |
|---|---|
| มอเตอร์ | เปิด/ปิด, watchdog 300–5000 ms, กลับทิศล้อแต่ละด้าน |
| เซอร์โวรวม | เปิด/ปิด PWM, ช่วงพัลส์ 500–2500 us, ความเร็วท่าทาง 25–200% |
| หัว / แขนซ้าย / แขนขวา | มุมต่ำสุด/สูงสุด, มุมพัก, trim ±30°, กลับทิศ |
| ไมค์ | เปิด/ปิด, รอบอ่าน, clap threshold, cooldown ของ beat, น้ำหนัก EMA |
| Ultrasonic | เปิด/ปิด, รอบวัด ≥60 ms, echo timeout, ชดเชยระยะ ±200 mm |
| Buzzer | เปิด/ปิด, สัดส่วน duty 0–100%, ความเร็วเพลง 50–200% |
| OLED | เปิด/ปิด, contrast 0–255, รอบแอนิเมชัน 100–1000 ms |
| Interactive | ระยะใกล้เกินไป, ระยะทักทาย, cooldown |
| ข้อมูลเว็บ | รอบ telemetry 250–5000 ms |

### บันทึกและคาลิเบรต

1. เปิดแท็บตั้งค่า Hardware แล้วแก้ค่าที่ต้องการ แต่ละช่องมีช่วงค่าที่รับได้ ค่าเริ่มต้น และคำอธิบาย ค้นหาชื่ออุปกรณ์ได้
2. ตรวจจำนวนค่าที่เปลี่ยน แล้วกด **บันทึกและใช้งาน** ข้อมูลจะถูกตรวจทั้งในเว็บและ firmware
3. เมื่อมีค่าเปลี่ยน ระบบหยุดมอเตอร์ เพลง และท่าทางก่อนบันทึก หลังบันทึกสำเร็จกลับ Manual และเซอร์โวที่เปิดอยู่เข้าสู่มุมพักใหม่ ค่าเดิมยังอยู่ถ้าบันทึกไม่สำเร็จ แต่การแสดงจะหยุดแล้ว
4. มุมจริงคำนวณจาก `(reverse ? 180 - คำสั่ง : คำสั่ง) + trim` แล้วจำกัดด้วย min/max ทุกท่า มุมพักหลังคำนวณต้องอยู่ในขอบเขต
5. บันทึก config ใน Preferences/NVS แบบ record เดียว มี schema version และ CRC32 โหลดอัตโนมัติหลังบูต หาก record เสียหรือไม่รองรับ ใช้ค่าเริ่มต้นและแสดงสถานะให้ทราบ ไม่เขียนซ้ำเมื่อค่าไม่เปลี่ยน และเว้นการเขียนอย่างน้อย 2 วินาที
6. หลายหน้าต่างใช้ revision ตรวจการแก้ทับกัน หากพบ config ใหม่ เว็บแจ้งให้โหลดค่าล่าสุดก่อนบันทึก โดยเก็บฉบับร่างเดิมไว้
7. **ใช้ค่าเริ่มต้นในแบบฟอร์ม** และ **นำเข้า config** เปลี่ยนเฉพาะฉบับร่าง ต้องกดบันทึกอีกครั้งจึงมีผล ส่งออก JSON ได้ทั้งค่าปัจจุบันและฉบับร่างที่ตรวจผ่าน
8. ทดสอบเซอร์โวด้วยปุ่มส่งตำแหน่ง หลังบันทึก config แล้วเท่านั้น การเลื่อน slider ยังไม่ขยับอุปกรณ์
9. คาลิเบรตไมค์ในพื้นที่เงียบ ระบบหยุดการแสดงแล้ววัด baseline 60 ตัวอย่างแบบไม่บล็อก ค่า baseline ไม่เขียน flash และวัดใหม่ทุกครั้งที่บูต / ใช้ config ใหม่

**หยุดทุกอย่าง** ตัดมอเตอร์และเสียงเมื่อหุ่นยนต์ได้รับคำสั่ง ยกเลิกท่าทาง/โหมดอัตโนมัติ และคงตำแหน่งเซอร์โวขณะนั้น ไม่ส่งคำสั่งกลับมุมพัก หากต้องการปล่อยแรงยึด ให้ปิดเซอร์โวใน config

### การใช้หน่วยความจำและ hardware

- HTML และข้อมูลเพลงยังอยู่ใน flash/PROGMEM ส่วน catalog และ schema ส่งเป็น JSON ด้วย buffer 384 bytes แทน String ขนาดใหญ่ Telemetry ใช้ buffer คงที่ 1024 bytes
- POST `/api/config` และ `/action` รับ form ผ่าน raw-body callback ลง buffer 2048 bytes จำกัดจำนวน argument ก่อนเรียกตัวแยก form ของ WebServer ไม่มี ArduinoJson เพิ่มเติม (ใช้ API ของ ESP32 core 3.3.12)
- ค่าเริ่มต้นเว็บเรียก telemetry ทุก 500 ms รอคำขอก่อนหน้าจบก่อนเรียกใหม่ และหยุด polling เมื่อแท็บถูกซ่อน แสดงสถานะ offline และแจ้งเมื่อข้อมูลอาจล้าสมัย
- Ultrasonic จับขอบ echo ด้วย interrupt แทน `pulseIn` ไม่รอ 22 ms ทุกครั้ง ไมค์อ่านแยกช่วงเวลา คาลิเบรตไม่ใช้ delay เป็นชุด และปฏิเสธ echo ที่มาหลัง timeout
- เซอร์โว 3 ตัวใช้ LEDC timer 0 (ช่อง 0, 1, 8 ตาม ESP32Servo 3.2.1); buzzer ใช้ช่อง 6 / timer 3 เพื่อแยกการเปลี่ยนความถี่ ไม่เพิ่ม PWM มอเตอร์ที่อาจชน timer
- มอเตอร์เว้น dead time อย่างน้อย 5 ms ก่อนสลับทิศ Watchdog ใช้ ESP timer task ตรวจทุก 5 ms แยกจากลูปเว็บ เปิดเสมอ หากสร้าง timer ไม่สำเร็จ ปฏิเสธคำสั่งเคลื่อนที่
- ปุ่มขับเคลื่อนส่งคำสั่งขณะกดค้างทุก 150 ms และหยุดเมื่อปล่อย ยกเลิก touch ออกจากหน้าต่าง หรือซ่อนแท็บ กรณีเน็ตขาดจริงใช้ watchdog ตามค่าที่บันทึกไว้
- OLED มี I2C timeout และตรวจพร้อมใช้งานก่อนวาด โหมด Party กลับท่าพักเพียงครั้งเดียวหลังเงียบ ลดการส่งภาพซ้ำทุกลูป
- แท็บสถานะระบบแสดง RAM ว่าง, RAM ว่างต่ำสุด, บล็อกว่างใหญ่สุด, uptime, รอบลูปสูงสุด, สถานะไดรเวอร์, IP, Wi-Fi RSSI และ revision ค่าพร้อมของ PWM ไม่ยืนยันแรงดันไฟหรือการต่อสายจริง

### HTTP API

ทุก endpoint ที่เปลี่ยนสถานะต้องส่ง `X-Robot-Request: 1` ไม่เปิด CORS การเรียกผ่านเว็บไซต์อื่นจึงไม่ผ่าน header นี้ แต่ header ไม่ใช่รหัสผ่าน ผู้ใช้ที่เข้าถึงเครือข่ายหุ่นยนต์ยังควบคุมได้ตามระบบเดิม

| Method / path | หน้าที่ |
|---|---|
| GET `/` | Dashboard |
| GET `/telemetry` | ข้อมูลสด / memory / ไดรเวอร์ |
| GET `/api/catalog` | เพลง สีหน้า ท่าทาง |
| GET `/api/config` | values, schema, revision, storage, schemaVersion, pins อ่านอย่างเดียว |
| POST `/api/config` | form `revision` + ค่าที่ต้องการเปลี่ยน; อนุญาต partial update, ปฏิเสธชื่อแปลก/ชื่อซ้ำ/ค่าไม่ถูกต้อง |
| POST `/action` | form `type`, `cmd`, และ argument ตามคำสั่ง |
| GET `/action` | รองรับ URL แบบเดิม แต่ต้องมี header ข้างต้น |

ตัวอย่างแก้ clap threshold โดยใช้ revision ล่าสุด:

```javascript
const current = await fetch('/api/config').then(r => r.json());
const response = await fetch('/api/config', {
  method: 'POST',
  headers: {'X-Robot-Request': '1'},
  body: new URLSearchParams({revision: current.revision, clap_threshold: 180})
});
console.log(await response.json());
```

## Interactive 2.3.1: ทักทายครั้งเดียว หาทางต่อ และเดินต่อเนื่อง

กด **Interactive** หรือ **เริ่ม Interactive อัตโนมัติ** เพียงครั้งเดียว
หุ่นจะเลือกสำรวจ หลบด้านหน้า ทักทาย จับเป้าหมายเคลื่อนที่ และตามเป้าหมายเอง
ไม่มีตัวเลือกพฤติกรรมย่อย ไม่มีขั้นตอนยืนยันเป้าหมาย เมื่อเสียเป้าหมายจะหยุด
วัดใหม่ แล้วกลับสำรวจหรือจับเป้าหมายใหม่โดยอัตโนมัติ

เปิดเครื่องยังเริ่มใน Manual ตามเดิม โหมด Interactive ที่เริ่มแล้วทำงานต่อ
แม้ปิดเว็บ กดหยุด Interactive / หยุดทุกอย่าง / ขับมือ เพื่อยกเลิก
การบันทึก config และเริ่มท่าทาง/Showcase ก็ยกเลิกโหมดอัตโนมัติ
ต้องเปิดมอเตอร์และ ultrasonic และตัวตัดมอเตอร์ต้องพร้อม จึงเริ่มโหมดนี้ได้

แก้อาการเดิน–หยุดจากรุ่น 2.2.0 ที่เดิน 120 ms แล้วรอ 600 ms พร้อมเก็บระยะใหม่
ทุกครั้ง รุ่นนี้ใช้ echo ใหม่ต่ออายุคำสั่งเดินหน้าโดยไม่ตัด GPIO ระหว่างคำสั่ง
ทิศเดิม จึงเดินต่อเนื่องเมื่อหน้าว่าง/เป้าหมายยังอยู่ไกลพอ ไม่เพิ่มความเร็วล้อ

Ultrasonic ยึดกับตัวหุ่น ไม่หมุนตามหัว ระหว่างเดินใช้ค่าระยะใหม่เพื่อรักษาระยะ
และหยุดก่อนสิ่งกีดขวาง ส่วนการจับเป้าหมายใช้หน้าต่าง 6 ค่าขณะตัวหุ่นอยู่นิ่ง
เท่านั้น ไม่ใช้การเปลี่ยนระยะจากการเดินของหุ่นเองเป็นหลักฐานว่าพบคน:

| เกณฑ์ตามลำดับ | การทำงานอัตโนมัติ |
|---|---|
| ไม่มี echo / ข้อมูลเก่า / อุปกรณ์ปิด | หยุด ปลดเป้าหมาย ล้างประวัติ รอข้อมูลกลับมาเอง |
| ระยะ ≤ `auto_stop_cm` | หยุดทันที อาจแสดงตกใจ/เสียงเตือนตาม cooldown |
| ยังไม่ครบ 3 ค่าต่างรอบ | หยุดสังเกตต่อ |
| ระยะกระโดดขณะอยู่นิ่ง > 4 × `target_delta_cm` | ล้างหลักฐาน เก็บข้อมูลใหม่หลังพักสั้น |
| ยังไม่มีเป้าหมาย และระยะเปลี่ยน ≥ `target_delta_cm` ในทิศเดียวกันสองการตัดสินใจต่างรอบ | จับเป้าหมายอัตโนมัติ ไม่รอคำสั่งจากเว็บ |
| จับเป้าหมายแล้ว และระยะ > `follow_distance_cm + 5` | เริ่มตามต่อเนื่อง ไม่บังคับหยุดเป็นช่วง |
| กำลังตาม และมัธยฐาน 3 ค่า ≤ `follow_distance_cm` | หยุดรักษาระยะ เริ่มใหม่เมื่อเกินระยะตามอีก 5 cm |
| echo ไกลกว่า `follow_max_cm` ครั้งเดียว | ไม่เพิ่มเวลาเดิน รอตรวจรอบใหม่ ไม่ปลดเป้าหมายจาก spike เดียว |
| echo ไกลเกินระยะสูงสุด 2 รอบติดกัน | หยุด ปลดเป้าหมาย วัดใหม่แล้วกลับสำรวจ |
| จับเป้าหมายแล้ว และเข้าโซนทักทายขณะหยุด | ทักทายหนึ่งครั้ง จบท่าหรือครบ 2.5 วินาทีแล้วคืนเซอร์โวสู่มุมพัก ปล่อยเป้าหมายและหาทางใหม่ |
| จับเป้าหมายแล้ว แต่รออยู่ระยะใกล้ครบ 2.5 วินาทีโดยไม่ได้เดินตามต่อ | ปล่อยเป้าหมายและหาทางต่อ ไม่รักษาระยะรอคนเดิมตลอดไป |
| กำลังหาทางหลังทักทาย/รอเป้าหมาย | ไม่จับเป้าหมายใกล้เดิมกลับมาทันที เลี้ยวตามขีดจำกัดจนมีทาง ≥ max(ระยะเริ่มสำรวจ, `proximity_greeting_cm + 20`, `follow_distance_cm + 10`) แล้วเดินสำรวจ |
| ยังไม่มีเป้าหมาย และระยะ ≥ max(`auto_clear_cm`, `auto_stop_cm + 13`) | เริ่มสำรวจต่อเนื่อง โดยคงช่วงเผื่อเริ่ม/หยุด 8 cm แม้ config เดิมกำหนดระยะโล่งชิดระยะหยุด |
| กำลังสำรวจ และระยะ ≤ max(`auto_clear_cm - 8`, `auto_stop_cm + 5`) | หยุดเดินหน้า แล้วสังเกต/เลี้ยวหลบ |
| สำรวจครบ max(3,000 ms, 4 × `auto_observe_ms`) | พักสังเกตระยะสั้นเพื่อหาเป้าหมายเคลื่อนที่ |
| มีสิ่งกีดขวาง แต่ยังห่างกว่า `auto_stop_cm` | เลี้ยวเป็นช่วง แล้ววัดใหม่หลังพักสั้น |
| ยังไม่พบทางหลัง `auto_turn_limit` ครั้ง | พัก `auto_observe_ms` แล้วลองเลี้ยวอีกด้านเอง ต้องมีข้อมูลใหม่และระยะปลอดภัย |

คงเพลง/เอฟเฟกต์ 19 รายการและโน้ต 443 ตัวเดิมทุกตัว เก็บโน้ตใน PROGMEM เช่นเดิม
ลด `Note` จาก 12 เหลือ 4 bytes: ความถี่ 16-bit, ความยาวเป็น tick 1/4 beat 8-bit,
และ dynamic 8-bit รวมข้อมูลโน้ตจาก 5,316 เหลือ 1,772 bytes ประหยัด Flash 3,544 bytes
(66.7% ของข้อมูลโน้ต ไม่ใช่ 66.7% ของ firmware ทั้งหมด) อ่านจาก Flash ครั้งละโน้ต
ไม่มีการสำเนาทั้งเพลงเข้า RAM และคำนวณเวลาตาม BPM/tempo ด้วยจำนวนเต็ม
ค่าจังหวะประจุดเดิมแทนได้ครบ สไตล์เสียงทั้ง 4 แบบคงเดิม

การเขียน `{NOTE_C5, N_QUARTER, DYN_MF}` ยังใช้รูปแบบเดิม ตัวแปลง constexpr
ทำงานตอนคอมไพล์ เพลงที่เพิ่มต้องมีระยะเป็นพหุคูณ 1/4 beat และไม่เกิน 63.75 beat
ข้อมูลเพลงเดิมอยู่ใน Flash อยู่แล้ว จึงไม่ได้อ้างว่าลด heap ของ ESP32 ลง 3.5 KB
firmware รวมมีส่วน UI และพฤติกรรมใหม่ จึงอาจใหญ่ขึ้นแม้ข้อมูลเพลงเล็กลง

ก่อนใช้งานจริง: ยกล้อเพื่อทดสอบเริ่ม/หยุดแต่ละโหมด แล้วทดสอบพื้นราบด้วยระยะใกล้,
ไม่มี echo, เป้าหมายออกด้านข้าง, เป้าหมายอยู่นิ่ง/เคลื่อนที่, สิ่งของแทนคน,
การตัดมอเตอร์เมื่อ HTTP ค้าง, การกดขับมือเพื่อยกเลิก และค่าที่เก็บไว้หลังรีบูต
การทดสอบในเครื่องพัฒนาไม่ได้อัปโหลดหรือยืนยันการเคลื่อนที่จริง


## การแก้ความหน่วงและมอเตอร์ · 2.3.2

ปุ่มหยุดกดได้ขณะคำสั่งก่อนหน้ายังค้างหรือสถานะเว็บออฟไลน์ ปล่อยปุ่มแล้ว
ยกเลิกการรอคำสั่งเดินและส่งหยุดด้วยเลขลำดับที่ใหม่กว่า คำตอบเก่าจะไม่สั่ง
หยุดทับการขับครั้งใหม่ การเปลี่ยนทิศ/โหมดรอให้คำสั่งหยุดเดิมได้รับการตอบรับ
ก่อนเริ่ม และการเปลี่ยนโหมด/หยุดทุกอย่างปฏิเสธคำสั่งเดินที่ออกก่อนหน้านั้น

เว็บส่งคำสั่งสดทุก 100 ms โดยคิดเวลารอเครือข่ายรวมในรอบ ส่งเดินทีละคำขอ
และหยุดการขับมือเมื่อไม่ได้คำตอบภายใน 350 ms พัก telemetry ขณะกดขับและ
ยกเลิก telemetry ที่กำลังรออยู่ ไม่เริ่มโหลด catalog/config ระหว่างกดขับ

คำสั่งเดินทุกคำสั่งจากเว็บต้องมี boot, client, seq, issued เพิ่มจาก type และ cmd:
- boot: driveBootId จาก telemetry ปัจจุบัน ต้องตรงกับการบูตครั้งนี้
- client: เลขสุ่มไม่เป็นศูนย์คงที่ในหน้าต่างนั้น
- seq: เลขลำดับเพิ่มขึ้นทุกคำสั่ง รวมคำสั่งหยุด
- issued: เวลาออกคำสั่งเทียบ uptimeMs ของ ESP32 เป็น uint32 ms

คำสั่งหมดอายุ 400 ms หลัง issued รวมเวลาที่รอในคิว หุ่นยนต์ใช้เฉพาะเวลา
ที่เหลือเป็น lease และไม่เกิน motor_timeout_ms จึงไม่ยืดเวลาเดินให้คำสั่ง
ที่มาถึงช้า เก็บเลขลำดับสูงสุดแยกได้ 4 หน้าต่างด้วยพื้นที่คงที่ ปฏิเสธ
หน้าต่างเพิ่มจนช่องเดิมว่าง 2 วินาที คำสั่งหยุดแบบเดิมที่ไม่มี seq และ
หยุดทุกอย่างยังใช้ได้ คำสั่งเดินแบบเดิมที่ไม่มีข้อมูลนี้ถูกปฏิเสธ: ต้องโหลด
dashboard ใหม่หลังอัปโหลด 2.3.2 ไม่ล้าง config/NVS เดิม

HTTP เว้นการรอ client ที่ยังไม่ส่งข้อมูลไว้ไม่เกิน 150 ms กำหนด idle timeout
ขณะอ่าน 100 ms และงบส่งต่อ response 350 ms ด้วยการส่งแบบไม่รอ socket
คำตอบใหญ่บนเครือข่ายช้ามากอาจถูกตัดและต้องโหลดใหม่ Parser ยังเป็นของ
ESP32 core; timeout เหล่านี้ไม่ใช่หลักประกันเวลาสูงสุดของทุก request
Watchdog มอเตอร์ยังทำงานแยกจากลูปเว็บ Wi-Fi ปิด modem sleep เพื่อลดเวลารอ
รับข้อมูล โดยใช้พลังงานวิทยุเพิ่มขึ้น

### ตรวจล้อซ้ายไม่หมุนทั้งเดินหน้าและถอยหลัง

โค้ดปัจจุบันใช้ Direct Digital Drive เต็มกำลัง ไม่มี PWM ปรับความเร็ว
setSpeed และ setTrim ไม่มีผล ล้อซ้ายใช้ GPIO 26/27 ล้อขวาใช้ GPIO 14/12
pin ทั้งหมดคงเดิม ค่ากลับทิศเปลี่ยนเพียงขั้วสัญญาณ จึงไม่ใช่หลักฐาน
ว่ามอเตอร์ซ้ายหรือไดรเวอร์ได้รับแรงดัน/กระแสจริง ระบบไม่มี encoder หรือ
เซนเซอร์กระแสและไม่สามารถยืนยันว่าล้อหมุนจาก telemetry ได้

1. ปิดไฟก่อนสลับสายมอเตอร์ที่ขั้วออกไดรเวอร์ซ้าย–ขวา ยกล้อพ้นพื้น
   แล้วลองเดินหน้า/ถอยหลังสั้น ๆ ไม่เปลี่ยนสาย GPIO
2. ถ้าอาการย้ายตามมอเตอร์: ตรวจสาย ขั้วบัดกรี มอเตอร์และชุดเฟือง/ล้อติดขัด
   ถ้ายังคงอยู่ช่องซ้าย: ตรวจช่องไดรเวอร์ สายเข้าจาก GPIO 26/27 และไฟเลี้ยง
3. วัดสัญญาณ GPIO 26/27 เทียบ GND: เดินหน้าควร HIGH/LOW และถอยหลัง
   LOW/HIGH (สลับกันเมื่อเปิด motor_left_reverse); หยุด LOW/LOW
   จากนั้นวัดแรงดันต่างระหว่างขั้วออกช่องซ้ายขณะต่อมอเตอร์ โดยเทียบกับช่องขวา
   และวัดไฟเลี้ยงขณะทั้งสองล้อเริ่มหมุนเพื่อดูแรงดันตก
4. ตรวจ GND ร่วมและให้แรงดันมอเตอร์อยู่ในช่วงที่รุ่นจริงรองรับ
   หากไดรเวอร์/มอเตอร์ร้อนและยังไม่หมุน ให้หยุดการทดสอบทันที

มอเตอร์ TT อัตราทด 1:48 สองตัวไม่ได้รับประกันรอบหมุนเท่ากัน
หลังแก้อาการไม่หมุนแล้ว การชดเชยความเร็วต้องมีการควบคุมแต่ละล้อจริง
และถ้าต้องการรักษารอบภายใต้โหลดที่เปลี่ยนต้องมีข้อมูลวัดรอบกลับมา
ดู [คำอธิบายจากผู้ผลิตมอเตอร์ Pololu](https://forum.pololu.com/t/romi-left-and-right-motor-way-off/21096)
และ [TI: กระแสขณะเริ่มหมุนและติดขัด](https://www.ti.com/video/6288082324001)
ห้ามใช้ค่ากระแสจากชื่อ TT/อัตราทดอย่างเดียวตัดสินว่าไดรเวอร์เพียงพอ

ผู้ใช้ระบุไฟเลี้ยงผ่าน stepdown 5V 3A; ยังไม่มีผลวัดแรงดันที่ขา VCC
ของไดรเวอร์ขณะเริ่มหมุน พิกัด 3A ไม่ยืนยันแรงดันจริงภายใต้โหลด
ถ้าเซอร์โวใช้ rail เดียวกัน ให้เทียบอาการขณะปิดเซอร์โวจาก config ด้วย
แล้วกลับมาใช้ค่าเดิมหลังตรวจ ไม่เพิ่มแรงดันเพื่อชดเชยก่อนรู้รุ่นมอเตอร์/ไดรเวอร์

## เซอร์โวและมอเตอร์ไม่ขยับ · 2.3.3

ใช้ตัวขับ LEDC ของ ESP32 core โดยตรงสำหรับเซอร์โว 50 Hz / 16-bit บน channel
0, 1, 2 ตรวจผลการสร้างสัญญาณและความถี่จริงก่อนรายงานว่าพร้อม ใช้ GPIO เดิม
18, 19, 23 และค่าพัลส์/มุม/กลับทิศ/trim ที่บันทึกไว้ครบ Buzzer ใช้ channel 6
และความละเอียด 10-bit ตามเดิม Core 3.3.12 เลือก timer ตามความถี่และความละเอียด
จึงไม่ได้อ้างว่าเลข channel กำหนดเลข timer ตายตัว

ไลบรารี ESP32Servo ที่ติดตั้งมีเส้นทางที่ตั้งสถานะ attached ก่อนตรวจผล
ledcAttachChannel ทำให้สถานะพร้อมไม่ยืนยันว่าเปิดสัญญาณได้จริง โค้ดชุดนี้
ตรวจผลจาก core โดยตรง ส่วน setTimerWidth ในไฟล์ไลบรารีที่ตรวจล่าสุดมีเงื่อนไข
กันการหารด้วยศูนย์แล้ว จึงไม่ยืนยันว่าจุดนั้นเป็นสาเหตุของอาการบนหุ่นยนต์
เว็บยังเชื่อมต่ออยู่และยังไม่มีผลวัดไฟหรือ log ที่ระบุสาเหตุทางกายภาพ

หน้า Hardware มีปุ่มทดสอบหัว/แขนซ้าย/แขนขวาแยกกัน เลื่อนมุมให้ต่างจากมุม
ปัจจุบันก่อนกด ทดสอบแต่ละตัวได้แม้เซอร์โวอีกตัวเริ่มไม่สำเร็จ ใช้ค่าที่บันทึก
แล้วเท่านั้น หากมี config ที่แก้ค้างไว้ให้บันทึกหรือโหลดค่าก่อนทดสอบ
หน้า Health แสดงสถานะแยกแต่ละเซอร์โว, ผลเริ่ม watchdog มอเตอร์ และสาเหตุบูต
ล่าสุด หาก motor_enabled หรือ servo_enabled ปิดไว้ เว็บแจ้งสาเหตุเมื่อกดสั่ง

หน้า Health มีปุ่ม "หยุดและเริ่มอุปกรณ์ใหม่" ซึ่งหยุดมอเตอร์/เพลง/ท่าทางและ
ยกเลิก Interactive ก่อนลองเริ่ม watchdog และสัญญาณเซอร์โวใหม่ เซอร์โวที่เปิดอยู่
จะกลับมุมพัก ปุ่มนี้ไม่ล้าง NVS และไม่เปิดอุปกรณ์ที่ปิดใน config ให้เอง
การลอง watchdog ซ้ำใช้ handle เดิมหลังเริ่ม timer ไม่สำเร็จ ไม่สร้าง timer รั่ว

ขณะกดขับ หน้าเว็บแสดง GPIO ล้อซ้ายและขวาจากคำตอบของบอร์ดโดยตรง ไม่ต้องรอ
telemetry ที่พักระหว่างขับ ลำดับคือซ้าย 26/27 และขวา 14/12; HIGH/LOW กับ
LOW/HIGH เป็นคนละทิศ LOW/LOW คือหยุดหรือช่วงเว้น 5 ms ก่อนเปลี่ยนทิศ
แสดงคำสั่งรอ, อายุคำสั่งล่าสุด และ lease ด้วย ข้อมูลนี้เป็นระดับ logic ที่ GPIO
ไม่ใช่แรงดันขั้วมอเตอร์ กระแส หรือ RPM ถ้าคำสั่งถึงและ GPIO เปลี่ยนแต่ล้อไม่หมุน
ยังต้องตรวจแบตเตอรี่, stepdown, GND ร่วม, ไดรเวอร์และสายตามขั้นตอนด้านบน

หลังอัปโหลดให้โหลดหน้าเว็บใหม่ ทดสอบโดยยกล้อพ้นพื้นและเว้นพื้นที่ให้แขนขยับ
